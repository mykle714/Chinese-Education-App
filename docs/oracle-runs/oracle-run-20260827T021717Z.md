### Guardrail evidence: stale-stamp bug on deterministic scripts

`backfill-tones` and `backfill-numbered-pinyin` are `deterministic: true` manifest
steps with no oracle interaction. Their row-selection is `tone IS NULL` /
`"numberedPinyin" IS NULL` — when a row already has the column populated (from
import) but was never run through this specific script, the script correctly reports
"0 pending" and exits **without calling `stampEntries`**, because it only stamps rows
it just wrote. `promote-discoverable.js` (correctly) checks the stamp, not the raw
column value, and reported all 25 rows `not ready: backfill-tones,
backfill-numbered-pinyin` even though the columns held valid data. Resolved via the
scripts' own `--stale` flag (`(col IS NULL OR staleClause())`), which stamps
populated-but-unstamped rows without re-deriving their values. This reproduces the
exact scenario the script's own code comment describes ("needed so a
populated-but-unstamped row can be stamped — the on-first-sort worker relies on
this"). No data was at risk; this is a planner/stamp-timing gap, not a correctness
bug, and the fix is the documented `--stale` flag, not a manual UPDATE.

### Planner staleness (informational, not a bug fix needed)

`oracle-plan.js`'s printed word list for `backfill-tones` / `backfill-numbered-pinyin`
matched the stale-stamp condition above exactly (6 and 25 words respectively) — its
report was accurate, not stale; the earlier "0 pending" reading from running the
scripts directly (without `--stale`) was the misleading one, since it reflects
"nothing left to *write*" rather than "nothing left to *stamp*". Recommend future
oracle rounds run tones/numbered-pinyin with `--stale` by default before trusting a
"0 pending" self-report as "fully stamped".
