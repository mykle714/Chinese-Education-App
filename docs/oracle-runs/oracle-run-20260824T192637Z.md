step earlier and never resurfaced as failing). Every cycle:

1. Exported prompts for all 17 rows.
2. Authored answers strictly per each prompt's own contract — verified

   character-for-character copy of one from that prompt's input array (no
   rephrasing, no added/dropped characters), matching the "never add, rephrase,
   or alter any string" rule every version of this script's system prompt states.
3. Applied — **`Updated: 0`, `Failed/invalid: 17` on all four cycles**, with the
   captured next-promptId alternating between exactly two sets:
   - Odd cycles: the "Pass 1 ranking" prompt (`Definitions: [...] → JSON array`).
   - Even cycles: the "critic" prompt (`Original input order` / `Junior's
     proposed order` → `{action, finalOrder, reason}`).

   Cycle-3's Pass-1 promptIds were **identical** to cycle-1's, and cycle-4's
   critic promptIds were **identical** to cycle-2's — the chain is oscillating
   between two states, not progressing toward a stamp/write. One word (理清)
   additionally showed the critic prompt echoing the *original* (unreordered)
   definition order even after I had explicitly authored a reordered Pass-1
   answer for it in an earlier cycle — on reflection the original order was
   linguistically correct anyway (literal sense before figurative, per the
   ranking principles), so I stopped fighting it and confirmed the original
   order, but the DB-write never landed regardless of what was confirmed.

Two content-persisting facts argue this isn't simple oracle mis-caching: my
cycle-3 reordered answers for 老式 and 花式 *did* show up verbatim as "Junior's
proposed order" in the cycle-4 critic prompt (so the intermediate reorder was

path in either `backfill-process-definitions-array.js` or the ORACLE MODE block
of `run-log.js`, not at anything in how I answered.

**Recommendation**: a developer should trace why a `"confirmed"` critic response
does not reach the script's DB-write branch, using the promptIds above
