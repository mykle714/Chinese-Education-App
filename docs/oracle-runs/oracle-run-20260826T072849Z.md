## Finding: planner/script staleness-model divergence (unstamped-but-filled rows)

The first export attempt (script's default row selection, no `--all-discoverable`) returned
**0 entries** for this exact 50-word batch, despite the planner reporting them pending.
Root cause, confirmed via direct psql: all 50 rows already had non-null `exampleSentences`
(3–6 entries from a prior, unstamped run) but carried **no stamp** in
`enrichmentLog['spanish/backfill-example-sentences']`.

- `oracle-plan.js` decides "pending" purely from the **stamp** (`enrichmentLog` vs manifest
  `version`).
- The script's own default SQL row-selection filter (`emptinessFilter`) decides "needs work"
  purely from **content** (`exampleSentences IS NULL OR '[]'`).

An unstamped-but-filled row satisfies neither gate the way the other expects: the planner
says "pending" (no stamp), the script says "nothing to do" (content already present). This
is a structural gap between the two staleness models, not a one-off data error — it will
recur for any row whose content was written outside a stamped run (e.g. an interrupted
earlier pass, or a hand-authored oracle round that predates the stamping convention).

**Workaround used (script-native, not a hand-written SQL bypass):** re-ran export/apply with
`spanish/backfill-example-sentences.js --all-discoverable`, which is the script's own
supported flag for removing the emptiness filter while keeping `validatedFilter` and
`wordsFilter` intact. This forced full regeneration + re-validation + re-stamping through
the real pipeline for exactly this 50-word scope. No `UPDATE ... SET` was hand-written.

**Suggested fix for a future session:** either have the planner additionally check row
content (not just the stamp) before calling a row "pending," or have
`oracle-plan.js` surface `--all-discoverable`-style scope hints when it detects this
mismatch, so a solo run doesn't have to rediscover the workaround from source.
