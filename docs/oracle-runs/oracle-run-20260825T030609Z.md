## 7. Bug found and fixed: `backfill-tones` / `backfill-numbered-pinyin` promotion-blocker desync

**Symptom**: `backfill-tones.js` and `backfill-numbered-pinyin.js`, run via oracle
export for the full 20-word batch, both reported "Found 0 DictionaryEntries needing
[tone/numberedPinyin] backfill... ✅ All entries already have data!" Immediately after,
`promote-discoverable.js --words=<batch>` (dry run) reported **all 20 words `✗ not
ready`**, every one blocked on `backfill-tones` and/or `backfill-numbered-pinyin`.

**Root cause**: both scripts are `deterministic: true` in the manifest and gate their
own row selection on the raw column (`tone IS NULL` / `"numberedPinyin" IS NULL`). These
20 rows already had both columns populated — inherited from the original cedict
import, which predates the run-log stamping system — so both scripts correctly found 0
rows matching their gate and exited without calling `stampEntries` on any row.
`promote-discoverable.js`'s completeness bar (`buildCompletePredicate` in
`server/scripts/backfill/shared/lib/requiredScripts.js`) does **not** re-derive
correctness from the column value; it checks the `enrichmentLog` jsonb stamp
(`present && version >= step.version`) for every applicable manifest step. Since these
rows were never stamped for these two scripts, the promoter correctly reported them as
incomplete even though the underlying data was already correct — a stamp/reality
desync, the same class of issue flagged for `spanish/backfill-process-definitions-array`
and `spanish/backfill-example-sentences` in earlier rounds this session.

**Fix**: both scripts already implement the documented mechanism for exactly this case
— a `--stale` flag whose gate becomes `(<column> IS NULL OR <staleClause>)`, where
`staleClause` matches rows with no stamp or a stamp below the current `SCRIPT_VERSION`.
Re-ran both with `--stale` against the same `--words=` batch:

```bash
server/scripts/backfill/run-prod.sh scripts/backfill/chinese/backfill-tones.js --words="$BATCH" --stale
# Found 8 DictionaryEntries needing tone backfill → 8/8 updated, stamped
server/scripts/backfill/run-prod.sh scripts/backfill/chinese/backfill-numbered-pinyin.js --words="$BATCH" --stale
# Found 20 DictionaryEntries needing numberedPinyin backfill → 20/20 updated, stamped
```

Both are deterministic, non-AI scripts — no oracle export/answer cycle was needed, only
the `--stale` recompute-and-stamp pass. No hand-written `UPDATE`, no bypass of either
script's own gate — the fix used the scripts' documented mechanism exactly as designed.

Re-running `promote-discoverable.js --words=<batch>` (dry run) after the fix: all 20
words `would promote`, 0 not-ready.

**Recommendation for a future round** (not acted on now — no authorization to modify
script code mid-run): any `--new` batch drawn from old/pre-pipeline corpus rows can hit
this same desync on other `deterministic: true` steps. Either (a) have `oracle-plan.js`
detect and surface it directly (diff the raw-column state against the stamp state for
deterministic steps) so it isn't only caught at the promotion dry-run, or (b) have these
scripts default to `--stale` behavior when invoked with an explicit `--words=` list,
since a targeted run is inherently narrow enough that the extra idempotent recompute is
cheap.
