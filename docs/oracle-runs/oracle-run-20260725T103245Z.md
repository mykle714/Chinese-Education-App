## 7. Bugs and findings — recorded, not fixed (§6 says keep going, so nothing here was patched)

### 7.1 A concurrent oracle session clobbered the global prompt log 🔴

`logs/backfill-runs.jsonl` shows a **Spanish** oracle run starting `00:25:32Z`, one
minute into this run. Both sessions default to the same two files
(`server/logs/oracle-prompts.jsonl`, `server/logs/oracle-answers.jsonl`), and
`capturePrompt` **appends**, so the two runs interleaved into one file.

Worked around by pointing this session at private paths:

```bash
BACKFILL_ORACLE_PROMPTS=$SP/<script>-p.jsonl BACKFILL_ORACLE_ANSWERS=$SP/<script>-a.jsonl
```

(the env overrides at `server/scripts/backfill/run-log.js:65-68`). Re-exporting after the
switch produced **byte-identical promptIds**, confirming the content hash is deterministic
and nothing had been mis-answered.

**Suggested fix:** default the two paths to something session-scoped (e.g. include the
run id from `logs/backfill-runs.jsonl`, or a PID) instead of a fixed filename, and have
`export` truncate rather than append. As written, two concurrent oracle runs silently
share a mailbox.

### 7.2 `isExclusivelyParenthetical` greedy-regex bug 🟠

`server/scripts/backfill/chinese/lib/orderGlosses.js:194-210`:

```js
export function isExclusivelyParenthetical(def) {
  return typeof def === 'string' && /^\(.*\)$/.test(def.trim());
}
```

The greedy `.*` matches **any** gloss that merely *starts* with `(` and *ends* with `)`,
not only glosses that are wholly parenthetical. So
`"(of trains) up (i.e. towards the capital)"` is treated as a bare qualifier and
demoted by `demoteLeadingParenthetical`, even though its real content ("up") sits
between the parens. Diagnosed by diffing the two `上行` prompt payloads.

**Fix would be** to reject strings whose parens close before the end — e.g. balance-scan
the string, or `/^\([^)]*\)$/` if nested parens are not expected. Not applied: §6
forbids stopping to fix bugs mid-run.

### 7.3 Planner/script disagreement on `backfill-tones` and `backfill-numbered-pinyin` 🟠

Both columns were already populated on the batch rows, but **unstamped** in
`enrichmentLog`. Result: the planner reports them pending forever (no stamp ⇒ pending),
while the scripts' own `doneGate` sees the populated column and does nothing — and
`promote-sortable.js` then blocks on the missing stamp. A genuine deadlock between the
manifest's staleness model and the scripts' gates.

Resolved **legitimately** with the scripts' own `--stale` flag
(`chinese/backfill-tones.js:26`), which re-runs and re-stamps. No SQL was hand-written.

**Suggested fix:** a one-off stamping sweep for rows whose tone/pinyin columns are
already correct, or make these two deterministic scripts stamp on a no-op pass.

### 7.4 `backfill-icons` sends the whole lead gloss to icons8 → HTTP 400 🟠

`backfill-icons` passes the entire first definition as the icons8 search term. Long,
citation-bearing cedict glosses blow the API's term limit and return **HTTP 400**,
which leaves `classifier`/icon data missing and therefore blocks `discoverable`.

Hit on **公学** (round 2, left at sortable). **马公** and **马公市** (round 3) carry the
same shape of gloss — `"Makung city in Penghu county 澎湖縣|澎湖县[Peng2 hu2 xian4]
(Pescadores Islands), Taiwan"` — and will hit it too when round 3 is resumed.

**Suggested fix:** truncate/normalize the search term (strip parentheticals, bracketed
pinyin and CJK, cap at a few words) before the icons8 call, and treat a 400 as a
skip-with-warning rather than a hard row failure.

### 7.5 My own driver bug (not a project bug)

My first sentence-reviewer harness keyed reject verdicts by **array index**, so every
repaired sentence was re-rejected on the next pass ("Flagged 3 / Repaired 3" every
round, forever). Fixed by keying on the exact Chinese sentence text. Worth recording
because it inflated the round-1 apply count considerably.

Two smaller driver fixes: the HSK prompt format is `Word: X\nPronunciation: …` (my
extraction regex assumed `Word: X (…)`), and the export log can contain duplicate
prompt lines, so answers must be de-duplicated by `promptId`.

## 12. Disclosure — the oracle authored *and* reviewed its own answers

Every prompt in this run was answered by me, including the pipeline's own reviewer/critic
links (POS review, cluster critic, sentence reviewer). Those links are real quality gates
against a *different* answerer; with one answerer on both sides they are weaker — they
caught mechanical faults (over-length gloss, punctuation mismatch, gloss/sense drift:
7 rejections total) but cannot be expected to catch a consistent misunderstanding of a
word. This is inherent to oracle mode and is not a defect of the run; the §11 list is
where that risk concentrates. Independent spot-checking of §10 and §11 by a human (or a
real API pass) is the appropriate mitigation.
