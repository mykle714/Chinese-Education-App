# Breakdown Feature Implementation Summary

## Overview
Added character breakdown support for Chinese vocabulary flashcards. Each Chinese vocab entry now includes a JSON breakdown showing the definition of each character.

> ### ⚠️ `breakdown` vs `components` — two different columns, one level apart
>
> Both live on `dictionaryentries_zh` and both "break a thing into smaller things",
> but they operate at **different levels and on disjoint rows**:
>
> | | `breakdown` | `components` (migration 125) |
> |---|---|---|
> | Rows | **MULTI**-character (`char_length(word1) > 1`) | **SINGLE**-character (`= 1`) |
> | Splits | a WORD into its characters | a CHARACTER into its visual parts |
> | Shape | `{char: {definition, sense}}` | `["相","心"]` (ordered, multiplicity kept) |
> | Example | 会议 → 会, 议 (each glossed) | 想 → 木, 目, 心 |
> | Carries | **meaning** (per-character glosses) | **shape** only (no glosses) |
> | Consumer | flashcard bt / on-card breakdown | word search No Pinyin hint ladder |
> | Generated by | `backfill-dictionary-breakdown.js` + `backfill-breakdown-senses.js` | `backfill-character-components.js` |
>
> A word's `breakdown` characters are exactly the rows whose own `components` the
> hint ladder reads, so the two chain: 想吃 --breakdown--> 想, 吃 --components-->
> 木/目/心, 口/乞. See [WORD_SEARCH_GAME.md](./WORD_SEARCH_GAME.md) §5a-ii.

### 3. Breakdown Generation Service
- **DictionaryService** (`server/services/DictionaryService.ts`):
  - Added `generateBreakdown(word: string, language: string)` method
  - Splits Chinese words into individual characters
  - Looks up each character in the dictionary
  - Returns JSON object with character definitions
  - Returns NULL for non-Chinese languages

- **VocabEntryService** (`server/services/VocabEntryService.ts`):
  - Updated `createEntry()` to automatically generate breakdown for Chinese vocab
  - Breakdown generated after entry creation
  - Fails gracefully if breakdown generation fails (doesn't break entry creation)

### 5. Backfill Scripts

Breakdown enrichment is two ordered passes over `dictionaryentries_zh.breakdown`
(breakdown is a per-word fact stored on the **det** table, not per-user on vet):

**5a. Generate breakdown (deterministic, no AI)** —
`server/scripts/backfill/chinese/backfill-dictionary-breakdown.js`
- Populates `breakdown[char] = { definition }` using each character's **global lead
  gloss** (`definitions[0]`) via `DictionaryService.generateBreakdown`.
- Scope: discoverable, multi-character (`char_length(word1) > 1`) zh entries with
  `breakdown IS NULL`; `--words=未来,摸脉` to target specific entries.
- Run-logged via `stampEntries`; progress tracking and error handling.
- `--stale` additionally re-selects rows stamped below `SCRIPT_VERSION` (via
  `staleClause()`, `server/scripts/backfill/run-log.js`). Two caveats before using it:
  - ⚠️ **It clobbers 5b.** The write is a wholesale `SET breakdown = $1` with
    `generateBreakdown`'s output, which carries **no `sense` key** — a `--stale` run
    erases every sense tag 5b wrote and reverts each gloss to the isolated-character
    lead. Follow it with 5b `--force`, or make 5a merge over the prior breakdown first.
  - It cannot detect the staleness that actually matters here. 5a's output is a
    function of *other rows'* `definitions`, so a later run of
    `backfill-process-definitions-array` on a component character silently invalidates
    every breakdown built from it (心服口服's breakdown was stamped 2026-07-03; 服's
    glosses were reordered 2026-08-11, leaving the breakdown showing the demoted
    `"Taiwan pr. [fu2]"` gloss). `staleClause()` compares a row's stamp to a code
    constant, never to another row's stamp — a dependency-staleness gate would need to
    compare `enrichmentLog` `ranAt` timestamps across the component characters.
- Usage: `node server/scripts/backfill/chinese/backfill-dictionary-breakdown.js`
- NOTE: the old per-vet `backfill-breakdown.js` was removed after the migration-66
  vet split / migration-73 legacy drop — this det-based script supersedes it.

**5b. Sense-tag the breakdown (AI)** —
`server/scripts/backfill/chinese/backfill-breakdown-senses.js`
- The `definitions[0]` gloss from 5a is the character's most-common sense **in
  isolation**, which is often WRONG inside a specific compound (会议 → 会 = "can"
  instead of the "meeting" sense; 银行 → 行 = "to walk" instead of the háng
  "row/business" sense). This pass picks the **correct `definitionClusters` sense**
  (migration 90) per component character in the context of `word1`.
- **Writes** (extends the breakdown shape, **no new column**):
  `breakdown[char] = { definition: <tagged cluster lead gloss>, sense: <tagged
  cluster's `sense` LABEL>, pronunciation? }`. The `pronunciation?` slot is
  **defensive only** — verified 2026-09-24, no writer emits it (0 of 7595 zh rows with a
  breakdown carry one, and `backfill-dictionary-breakdown.js` never sets it), so read
  paths must not depend on it. `sense` is the source of truth and is
  the cluster **label** (not an index) so it survives re-clustering/re-scoring — the
  same stability contract as `vet.selectedSense` (migration 99). `definition` is
  refreshed to that cluster's lead gloss (ddt-style) so the on-card breakdown shows
  the correct sense with **no read-path change**.
- **Method** (mirrors the example-sentence per-segment sense tagger): per unique
  component character — 0 clusters → left untouched (no `sense`); 1 cluster →
  auto-assigned, no API call; ≥2 clusters → offered to one Sonnet call per word that
  returns `{char: senseLabel}`. Each label is validated against that character's own
  cluster labels; invalid/missing → falls back to the most-frequent cluster and
  prints a `⚠ BREAKDOWN SENSE REVIEW` line (stable marker, greppable by the
  mark-discoverable agent — same convention as the clusterer).
- **Depends on** 5a (breakdown must exist) **and** the component characters being
  clustered by `backfill-cluster-definitions.js` first; an un-clustered component
  char is carried through unchanged and fixed on a later re-run.
- Flags: `--words=会议,银行`, `--all` (include non-discoverable), `--force` (re-tag
  rows already carrying a `sense`), `--stale` (below `SCRIPT_VERSION`),
  `--reconcile` (**sense drift** — see below), `--limit=N`, `--spot-check`
  (5 entries, NO writes, verbose).
- Usage: `docker exec cow-backend npx tsx scripts/backfill/chinese/backfill-breakdown-senses.js`

#### 5b-drift. Orphaned sense labels — the third staleness axis

Storing the cluster **label** rather than its index buys stability across
re-clustering and re-scoring, but **not across a RELABEL**. When
`backfill-cluster-definitions.js` runs again on a component character it may rename or
drop the label 5b stored, and the pointer then resolves to nothing:

- the stored `definition` **freezes** at whatever the cluster said when it was tagged;
- the model's choice can no longer be audited or refreshed against the live clusters;
- **nothing notices** — the row's `enrichmentLog` stamp is still current, and 5b's own
  gate ("breakdown text already contains `sense` ⇒ done") excludes the row forever.

A 2026-08-28 audit of the dev corpus found **1143 of 8724 stored senses (13%)
orphaned**, concentrated on the *commonest* characters (大 36 words, 水 35, 有 30,
高 29, 电 28, 手 19) — i.e. a bulk relabel, not a long tail. The symptom that surfaced
it: 下手's 手 stores `"personally / by hand"`, which matches no current 手 cluster
(nearest: `"personally / first-hand"`), and the gloss it froze — `personal` — is the
wrong sense for 下手 in the first place.

**Detection** lives in the enrichment manifest as a *drift probe*:
`DRIFT_PROBES.breakdownSenseOrphan` in
`server/scripts/backfill/shared/lib/requiredScripts.js`. Drift is a **cross-row**
signal — whether this row is stale depends on the COMPONENT characters' rows — so it
cannot compile into `buildIncompletePredicate` like `when` and `version` do. It is a
set-returning query the caller runs once per round; `oracle-plan.js` →
`runDriftProbes` OR-s its ids into the candidate scope and passes them to
`pendingSteps`/`isComplete` as the 4th argument `driftedStepIds`, so a drifted row is
re-planned and cannot promote. Keep the query **set-based** (`LEFT JOIN … IS NULL`):
the correlated `NOT EXISTS` form takes >120 s on the zh corpus, the joined form ~30 ms.

**Repair** is `--reconcile` on 5b, which re-tags exactly the drifted rows using that
same probe query. Without it the only escape was `--force`, which re-tags all ~9.5k
rows — and re-spends every prompt — to fix the ~1k that actually drifted.

Referenced code: `backfill-breakdown-senses.js` (`RECONCILE`),
`shared/lib/requiredScripts.js` (`DRIFT_PROBES`, `driftProbesFor`, `pendingSteps`,
`isComplete`), `oracle-plan.js` (`runDriftProbes`),
`server/__tests__/driftProbes.test.ts`.

**5c. Explain the literal translation (AI)** —
`server/scripts/backfill/chinese/backfill-breakdown-elaboration.js` (`SCRIPT_VERSION` 2)
(column added by `database/migrations/133-add-breakdown-elaboration-to-zh.sql` —
authored as 130, renumbered to 133 in merge `ef7b964` when origin's per-language
minute-points migration claimed 130)
- The breakdown rows say WHAT a word is made of; this note says WHY the parts add up.
  The preferred note explains the **literal translation**: the characters read in order
  as a blunt English phrase, opened in curly quotes, then what that phrase pictures and
  how the picture becomes the meaning — naming the symbol when a concrete thing stands
  for something abstract (hand → deliberate action, heart → mind/feelings, mouth →
  speech, eyes → attention/envy):
  - 住手 → *“Stop hand”: stop moving your hand. The hand stands for whatever you're doing.*
  - 火车 → *“Fire vehicle”: named in the steam age when trains ran on burning coal.*
- The model labels each answer with a **kind**, used only to validate the note's shape
  (`shapeProblem`) and **not stored**:

  | Kind | When | Shape |
  |---|---|---|
  | `image` | the literal translation pictures something that bridges to the meaning — the common case; **mild images count** (火车, 开心, 东正教's calque of "orthodox") | opens with “translation”: |
  | `origin` | only makes sense through a story/allusion/fossilized phrase (矛盾, 吃醋) | opens with “translation”: |
  | `sound` | transliteration (沙发, 波兰斯基) | NO translation — "Chosen for sound, to spell out “sofa”. …" |
  | `null` | literal translation IS the definition (学生, 会议, 学堂), function words (然而), suffix-only compounds, disputed origins (东西, 马虎) | column written NULL |

  The picture must come FROM THE WORD (a real sense, real history, a real calque): a note
  that needs an invented simile ("like a dot on a map") is `null`. The word "Literally"
  is never written — the quotes alone mark the translation.
- **History.** v1 (to 2026-11-07) asked "is this breakdown OPAQUE?" and called mild
  metaphor "straightforward", so it dropped exactly the 住手 / 动手 / 放心 family, and
  drifted into "Here 等 means 'equal'" sense corrections its prompt forbade (11,108 of
  27,595 dev rows held a note vs a ~30% design). v2 inverts the question. The manifest
  bump to 2 re-plans every multi-char row, and a re-judge CLEARS v1 notes whose v2
  verdict is `null` (the script always writes the column).
- **Writes** `dictionaryentries_zh."breakdownElaboration"` (text, nullable). The literal
  translation lives inside the note; there is deliberately **no separate column** for it.
- ⚠️ **NULL is a real answer, not "not yet computed."** Evaluated-ness lives in the
  per-entry `enrichmentLog` stamp (migration 68) under `chinese/backfill-breakdown-elaboration`,
  written for every decided row **including the NULL ones**; the script's default WHERE
  gate reads that stamp, never `breakdownElaboration IS NULL`. Any future consumer asking
  "which rows still need judging?" must do the same.
- **Length cap**: 100 characters for a 2-character word, 150 for 3+ (`capFor`) — a CAP,
  not a target; the prompt says so, because a stated length becomes the length. An
  over-cap answer is retried ONCE with the overage quoted back and a limit of
  `RETRY_FRACTION` (0.8) of the cap (models told "at most 100" land at 101–104); a second
  over-cap answer is left **unwritten and unstamped** (⚠ review line). Prose is never
  truncated.
- **Parsing** (`parseVerdict`, `normalizeQuotes`): the note is full of quotation marks,
  and Sonnet 4.6 rewrites the prompt's curly “…” as straight "…" — unescaped inside the
  JSON string, which breaks `JSON.parse`. The parser falls back to a tolerant extraction
  (explanation = everything up to the last quote before the closing brace), and every
  stored note has its straight double quotes normalized to curly ones, so the display is
  uniform whichever model or oracle answerer wrote it.
- Human-review lines use the marker `⚠ BREAKDOWN ELABORATION REVIEW` (same stdout
  convention as the clusterer and 5b); an unparseable line quotes the raw response.
- **Depends on** 5a (breakdown must exist) and, for a trustworthy literal translation,
  5b (in-context senses). The prompt also tells the model to silently use the right sense
  when a shown gloss is plainly wrong, and never to comment on the correction.
- **Model**: `MODEL` = `claude-sonnet-4-6` for direct API runs. The PPE cron runs this
  step in oracle mode (`run-log.js` → ORACLE MODE), where the prompt, not `MODEL`, decides
  quality. The prompt was tuned on `claude-opus-5-5` (effort `low`); on Sonnet 4.6 it is
  weaker at declining disputed origins (wrote the 东西 market folk etymology) and
  occasionally self-revises mid-answer (unparseable → flagged, unstamped).
- Flags: `--words=住手,马虎`, `--all`, `--force` (re-decide stamped rows; a verdict that
  flips to `null` CLEARS the stale note), `--limit=N`, `--spot-check` (5 random entries
  or the `--words` set, NO writes, verbose). `--stale` is accepted but is a no-op: the
  default gate is `staleClause()` (never stamped OR stamped below `SCRIPT_VERSION`) —
  the same "pending" definition as `oracle-plan.js`, which hands scripts a bare
  `--words=` list. A gate of "never stamped" alone would leave every row stamped at an
  older version re-planned and skipped forever after a version bump.
- Usage: `docker exec cow-backend npx tsx scripts/backfill/chinese/backfill-breakdown-elaboration.js`
- **Consumer**: the eip breakdown tab renders it as "How the parts make the word" under
  the rows — see Frontend Integration below.

## Data Flow

### Creating New Chinese Vocab Entry:
1. User creates vocab entry through API
2. Entry is saved to database
3. If language is 'zh', breakdown is automatically generated
4. Breakdown is saved to entry
5. Client receives entry with breakdown included

### Fetching Flashcards:
1. Client requests flashcards from `/api/onDeck/distributedWorkingLoop`
2. Server queries `vocabentries` table
3. Breakdown column is automatically included in response
4. Client receives `VocabEntry` objects with breakdown field populated

### Frontend Integration — DONE

`src/utils/breakdownUtils.ts` → `getBreakdownItems(entry)` turns the `breakdown` map into
one `{ character, pinyin, definition }` per character **in the word's own order**, zipping
each glyph with its syllable from `entry.pronunciation` and falling back to the map's own
`pronunciation`. Characters missing from the map are dropped, so a null or partial
breakdown degrades to fewer rows rather than to placeholders.

**One row component, both surfaces: `src/features/flashcards/BreakdownRow.tsx`** (the
design's `.bkr`, 2026-08-24; restyled 2026-10-29 as the Tower Tier 2 `.bk` — each character an outlined card in the eip palette's `card` fill). Rendered in ONE place, the eip's breakdown tab
(`FlashcardsLearnPage/InfoCardTabContent.tsx`), and every surface reaches it through that
tab: the **dictionary cdp** mounts the eip panel itself (`InfoCardPanelBody`, 2026-10-10 —
its own Character Breakdown box in `VocabCardDetailBody.tsx` is gone), and the **saved-card
cdp** raises `InfoCardSection` directly and drills in by NAVIGATING to the tapped
character's card detail instead of opening a nested eip tab
(`VocabCardDetailPage.handleWordOpen`).

It replaced a wrapping grid of 1:1 block buttons (`InfoCardBlockButton`, deleted), for two
reasons worth keeping:

- **A square sized to the character clips the GLOSS**, which is the part being read.
  "to pass; to cross; to go over" does not fit 116px at a legible size.
- **A grid says "peers to choose between".** A breakdown is not a menu — it is the word
  taken apart in ORDER, and order is what a column of rows shows and a wrapping grid
  destroys the moment it wraps.

A row is glyph column (fixed 52px holding an `md` cpcd — rows are always one character,
so it can run larger than a word would; fixed so every gloss starts on the same margin)
with the reading **under the glyph** as the cpcd's own pinyin line (tone-coloured via
`useToneColor`, exactly like every other `CPCDRow`; 2026-10-10 — it used to be a separate
text line above the gloss) → the gloss (`SIZE.body`) → a chevron. Tapping one opens that
character's own entry; inside the eip the **word trail** at the top of the panel is how you
come back.

**The breakdown note** (Artboard 25's titled paragraph, *"How the parts make the word"*,
built 2026-11-07) renders under the rows when the entry carries a `breakdownElaboration`
(§ 5c): an `EipSectionLabel` heading over a body paragraph styled like the definition tab's
long definition (`SIZE.body`, `fc.onSurface`, `FC_FONT`, line-height 1.6). No note → nothing
renders. Shown as stored, so a row still on a v1 note shows that note until the backfill
re-runs it (owner's call).

How it reaches the tab — one column on each read path, no new prop (the tab reads
`currentEntry.breakdownElaboration`):
- **Saved-card reads**: `server/dal/shared/dictJoin.ts` → `DICT_COLS` / `dictLateralSelect`
  (the es branch selects `NULL::text`) → `VocabEntryBase.breakdownElaboration`.
- **Det reads / every drill-in / the acp's info lookup**:
  `server/dal/implementations/DictionaryDAL.ts` → `DICTIONARY_COLUMNS` (es gets
  `NULL::text` via `dictionaryColumns`) and `mapRowToEntity` →
  `DictionaryEntryBase.breakdownElaboration` → `src/utils/dictEntryAdapter.ts` →
  `dictionaryEntryToVocabEntry`.
- **Render**: `src/features/flashcards/FlashcardsLearnPage/InfoCardTabContent.tsx`
  (`.mobile-demo-breakdown-elaboration`).
`DiscoverCard` (acp sort cards) does NOT carry it: the acp opens the eip through the
dictionary lookup, not from the card.

**Single-character words have no breakdown at all** and get a "Used In" list instead
(`UsedInPaginatedList`) — the same slot, a different question.
