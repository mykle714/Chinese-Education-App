## Process finding: doneGate vs promotion-gate stamp mismatch

`backfill-tones.js` and `backfill-numbered-pinyin.js` both gate on `<col> IS NULL` by
default, so a row whose `tone`/`numberedPinyin` column is already populated (from an
older, pre-stamping enrichment path) reports "0 rows needing backfill" — but
`promote-discoverable.js`'s completeness predicate (`buildCompletePredicate` in
`server/scripts/backfill/shared/lib/requiredScripts.js`) checks the `enrichmentLog`
stamp, not the column, and blocked all 20 words citing these two steps as incomplete
(confirmed via read-only inspection: 文员/id 50917 had `tone`/`numberedPinyin`
populated but no `enrichmentLog` key for `chinese/backfill-numbered-pinyin`, and no
stamp at all in 4 other rows for `backfill-tones`). This is not a version mismatch —
manifest and script agree on `version: 1` for both. It is a **missing stamp** on rows
whose data predates the stamping mechanism.

Fix applied (no hand-written SQL): re-ran both scripts with `--stale`, which OR's
`staleClause()` into the doneGate and picks up populated-but-unstamped rows; both are
deterministic (no AI/oracle call), so `--stale` re-computed (no-op, same values) and
`stampEntries` wrote the missing `enrichmentLog` keys directly. 5 rows needed
`backfill-tones --stale`, 20 needed `backfill-numbered-pinyin --stale`. After the
re-stamp, `promote-discoverable.js` cleared all 20 rows on the next dry-run.

**Worth follow-up**: any future batch touching pre-existing (non-freshly-imported)
rows could hit the same silent block. Consider whether `oracle-plan.js` should surface
"populated but unstamped" as a distinct category from "column null" so this doesn't
need ad-hoc diagnosis each time it recurs.
