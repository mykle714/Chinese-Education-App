### Issue found and fixed: promotion dry-run caught 3 missing/unstamped steps

The working notes (`server/logs/oracle-run-notes.md`) listed only 14 steps as the full
manifest and marked all 14 done. The **first promotion dry-run** (before this report was
written) showed all 25 words `✗ not ready`, blocked on `backfill-tones`,
`backfill-numbered-pinyin`, and (for 13 of the 25) `backfill-classifier` — none of which
had ever appeared in the run notes' manifest.

Root cause, confirmed by reading `requiredScripts.js`: `pendingSteps`/`isComplete` are
**purely stamp-based** (`enrichmentLog[stepId].version`), independent of whether the
underlying column already has data. `backfill-tones` and `backfill-numbered-pinyin` are
`deterministic: true` scripts whose default gate is `tone IS NULL` / `"numberedPinyin" IS
NULL` — since this batch's tone/pinyin data was already populated (from initial import,
not from this pipeline), the scripts found "0 needing backfill" on a normal run and never
called `stampEntries`, so the rows stayed permanently "pending" from the planner's
perspective. Re-running both with `--stale` (which ORs `staleClause()` into the gate)
correctly force-stamped the already-correct data: 16/16 for tones, 25/25 for
numbered-pinyin.

`backfill-classifier` was a genuine gap — it was never run at all in the original 14-step
pass, apparently omitted from the working notes' manifest by mistake. Ran it export→author→
apply cleanly (single round, no retries): 25 prompts captured, 25 answers authored, 25
updated, 0 errors.

**Lesson for future rounds**: do not treat the run notes' manifest as authoritative once
enrichment starts — re-run `oracle-plan.js` (or `promote-discoverable.js` in dry-run) right
before promotion to catch any step the working notes missed or any deterministic step that
silently skipped its stamp.
