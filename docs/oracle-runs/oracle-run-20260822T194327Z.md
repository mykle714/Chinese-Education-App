## ⚠ The serious problem this round found

**Two unsharded oracle workers raced the identical batch, and it orphaned 20 of 36 example
sentences on live rows.**

A long-running interactive session (`claude --dangerously-skip-permissions`, pid 4093553, up
8 days) was working the same `--new` planner scope with no `--shard` at the same time as this
cron round. Both invocations are told "solo … do not pass `--shard`", so both drew the
byte-identical `ORDER BY … LIMIT` batch — exactly the collision §6b of the skill describes.

The damage is not a lost write; it is a **dangling foreign key inside the row**. The other
worker wrote `definitionClusters` and then `exampleSentences` (whose per-sentence `sense`
field keys back into the cluster list). This worker then rewrote `definitionClusters` with
different `sense` labels. The sentences now point at senses that no longer exist:

| word | orphaned sentence `sense` | sentences affected |
|---|---|---|
| 代代 | "passing on through successive generations" | 3 / 3 |
| 年度 | "year (as a period)" | 3 / 3 |
| 度数 | "numerical reading in degrees" | 3 / 3 |
| 度日如年 | "time drags painfully" | 3 / 3 |
| 度过 | "to spend / get through (time)" | 3 / 3 |
| 教主 | "leader of a religion" | 3 / 3 |
| 度 | "times / occurrences", "to spend or pass (time)" | 2 / 3 |
| 教 | "to make somebody do something" | 1 / 3 |

Detection query:

```sql
SELECT d.word1, es->>'sense' AS es_sense,
  EXISTS (SELECT 1 FROM jsonb_array_elements(d."definitionClusters") c
          WHERE c->>'sense' = es->>'sense') AS matches_cluster
FROM dictionaryentries_zh d, jsonb_array_elements(d."exampleSentences") es
WHERE d.language = 'zh' AND d.discoverable
ORDER BY 3, 1;
```

**Not repaired in this round** — a repair regenerates ~24 sentences, and doing it while the
other worker is still live would simply re-orphan them. Remediation, once exactly one worker
is running:

```bash
server/scripts/backfill/run-prod.sh scripts/backfill/chinese/backfill-example-sentences.js \
  --all-discoverable --words=代代,年度,度,度数,度日如年,度过,教,教主
```

**The structural fix is the important one:** either give the two workers `SHARD=1/2` and
`SHARD=2/2`, or stop running two at all. `oracle-cron.sh`'s `flock` does not help — it only
guards against two *cron* rounds, and the second worker here is an interactive session.
Worth considering whether the run-wide detection query above belongs in §5 of the skill, since
nothing in the current verification set would have caught this.

## Other findings

- **The short-gloss stage manufactured its duplication for the fourth consecutive round**
  (r514, r515, r516, r517). It fires purely on the LEAD gloss exceeding 20 characters, so
  年度 — whose array already contained "annual" and "year" — got a *third* short rendering
  ("fiscal/school year"), and 度日如年, which already had "days drag like years" and "time
  hangs heavy", got "time crawls". Suggested fix unchanged: skip the stage when the array
  already holds a substantive gloss ≤ 20 chars, or *replace* the long lead rather than
  prepend to it.
- **`process-definitions-array` re-processes rows it just wrote.** Its selection is
  content-based, so a successful write re-hashes the pass-1 prompt and the row returns for
  another full pass-1 + critic cycle. It converges after one extra pass, but every row it
  actually changes costs double the prompts. 12 rows needed 38 prompts where 22 would do.
- **`cluster-definitions` scores one cluster per apply pass.** 度 (5 clusters) required five
  separate export→author→apply cycles, each a full process start-up against prod. Batching
  the per-cluster frequency prompts into one call per row would cut this round's wall-clock
  by a large fraction.
- `/tmp/oracle-r517/pdaloop.py` now refuses any prompt containing `(primary reading:` — the
  guard the r516 report asked for. It fired correctly twice (once on a clustering prompt,
  once on a frequency-score prompt), so no stage was auto-answered that shouldn't have been.
