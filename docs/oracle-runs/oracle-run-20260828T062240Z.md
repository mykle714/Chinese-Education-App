## Recurring gap: tones/numbered-pinyin stamp under-reporting

Both scripts gate on `<col> IS NULL`. When the column was already populated by the
original import (not by this backfill script), the gate finds nothing to do and
never calls `stampEntries` — but `promote-discoverable.js`'s completeness bar
requires the `enrichmentLog` stamp, not just the column value. Net effect: a row
can have correct data and still block promotion as "not ready: backfill-tones,
backfill-numbered-pinyin". Fixed here (again — same pattern seen in the
`2026-08-28T02:32:06Z` round) by re-running both scripts with `--stale`, which is
deterministic and safe to re-apply (recomputes the same values, stamps the row).
This is now a confirmed repeatable gap, not a one-off; worth a permanent fix
(stamp on `col IS NOT NULL` too, or align the planner's own "pending" count with
`promote-discoverable.js`'s bar — the planner reported non-zero pending counts for
both scripts that turned out to be stale/wrong).
