## 1. es `--discoverable` refresh — dead end, two script bugs found

Both are manifest-vs-script gate mismatches, same shape as the zh `always`-step issue
found later in this round (§3):

- **`spanish/backfill-process-definitions-array.js`** never stamps a row it leaves
  unchanged (my authored Pass1 ranking matched the existing DB order exactly). The
  script's own `doneGate` treats "no change needed" as "nothing to do" and returns
  without calling `stampEntries`, so the manifest step stays perpetually pending for
  any es row whose definitions are already in the right order.
- **`spanish/backfill-example-sentences.js`** has no `--stale` escape hatch (unlike
  the zh tone/pinyin scripts), so there is no way to force-stamp an es row whose
  `exampleSentences` column is already populated but was never stamped by this
  script version.

Net effect: no es `--discoverable` row could be walked to a clean promote-eligible
state this round. Recommend giving both scripts the same `--stale`-driven stamp path
`chinese/backfill-tones.js` already has (see §3) — it is the general fix for
"data present, stamp missing" across the whole pipeline, not zh-specific.

## Operational lesson: oracle-answers.jsonl must accumulate across chained apply calls

Several scripts internally chain multiple sequential API calls per row (e.g.
`cluster-definitions` reuses `orderGlosses.js`'s pass1/critic, then does its own
clustering + per-sense frequency calls; `example-sentences` chains
generate → review → per-sentence segment-tagging, one segment-tagging call *per
sentence*). Critically, **`apply` replays the entire chain from the first stage on
every invocation** — it does not resume from where a prior `apply` left off. This
means `oracle-answers.jsonl` must hold the union of every promptId ever produced for
that script+word combination, never just the newest batch. Overwriting it with only
the latest stage's answers makes `apply` immediately fail asking for the
earlier-stage promptIds again, which looks like (but is not) an export/apply reset.
I hit this 3 times this session before settling into an append-only pattern for this
run; the fresh continuation stayed append-only throughout and had no repeat
incidents. Worth a comment in `run-log.js`'s oracle-mode block for the next agent.

## Manifest quirk confirmed: unstamped "always" steps

`backfill-tones` and `backfill-numbered-pinyin` are `when: 'always'` manifest steps
whose gate is `column IS NULL`. When the column is already populated (data
pre-existing from import), the script's own early-exit path never calls
`stampEntries`, so the manifest keeps listing the step as pending indefinitely even
though there is nothing to compute. Both scripts already ship a `--stale` flag
specifically for this (per their own header comments — "needed so a
populated-but-unstamped row can be stamped"); using it resolved this cleanly. The
same fix does not yet exist on the es scripts flagged in §1 — that's the concrete
change recommended there.
