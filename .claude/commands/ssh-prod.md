# SSH to Prod (dev box → production server)

Reach the production machine from the dev box over SSH. This is what makes prod work
runnable directly instead of handed to the user as a copy-paste block.

**Prod is a SEPARATE physical machine from dev.** Older docs claimed prod and dev were
"the same machine with containers side by side" — that is false and caused real confusion.
Dev has only `cow-*-local` containers; prod has only `cow-*-prod`.

## Connection

```bash
ssh -i ~/.ssh/id_ed25519_cow_prod michael@174.127.171.187
```

| Fact | Value |
| --- | --- |
| SSH target | `michael@174.127.171.187` |
| Key | `~/.ssh/id_ed25519_cow_prod` (ed25519, no passphrase, dev-box only) |
| Prod hostname | `beech-2025` |
| App directory | `~/vocabulary-app` |
| Containers | `cow-backend-prod`, `cow-frontend-prod`, `cow-postgres-prod` |
| Marker file | `~/vocabulary-app/amIOnTheProdMachine.md` → "This is the prod machine." |

### ⚠️ The address is `.187`, NOT `.180`

`174.127.171.180` appears in several older docs and is **wrong** — nothing answers there.
A connection attempt fails at the network layer with `No route to host`, and the ICMP
unreachable is generated by our own address, so it is not a firewall you can open:

```
$ ping 174.127.171.180
From 174.127.171.187 icmp_seq=3 Destination Host Unreachable
```

`174.127.171.187` is this site's real public address (confirmed against `api.ipify.org`).
The two are adjacent in the same ISP /24, which is exactly why the stale value looked
plausible for so long. **If a doc says `.180`, the doc is stale — fix it.**

### Non-interactive use

Always pass `-o BatchMode=yes` when scripting, so a missing key fails immediately instead
of hanging on a password prompt that no agent can answer:

```bash
ssh -o BatchMode=yes -i ~/.ssh/id_ed25519_cow_prod michael@174.127.171.187 'hostname; whoami'
```

Prefer one `ssh` invocation carrying a multi-line script over many round trips.

## Reaching prod's Postgres (tunnel)

`cow-postgres-prod` is published on prod's **loopback only** (`127.0.0.1:5432`), so it is
not reachable across the network. Two ways in:

**A. Run psql inside the container** — simplest for queries, needs no password:

```bash
ssh -o BatchMode=yes -i ~/.ssh/id_ed25519_cow_prod michael@174.127.171.187 \
  'docker exec cow-postgres-prod psql -U cow_user -d cow_db -c "SELECT max(version) FROM schema_migrations;"'
```

For multi-statement SQL, **pipe a local file into `docker exec -i`** rather than nesting
quotes — quoting SQL through two shell layers is where this reliably goes wrong:

```bash
ssh -o BatchMode=yes -i ~/.ssh/id_ed25519_cow_prod michael@174.127.171.187 \
  'docker exec -i cow-postgres-prod psql -U cow_user -d cow_db -v ON_ERROR_STOP=1' < local.sql
```

**B. Port-forward** — required when a tool on the dev box must hold connections to BOTH
databases at once (this is the only reason to prefer it; `/gloss-groups-push` is the case
that needs it):

```bash
ssh -f -N -o BatchMode=yes -o ExitOnForwardFailure=yes \
  -L 15432:127.0.0.1:5432 -i ~/.ssh/id_ed25519_cow_prod michael@174.127.171.187
```

Prod DB then answers on `127.0.0.1:15432` from the dev box. `-f -N` backgrounds it with no
shell; `ExitOnForwardFailure` makes a bind collision fail loudly instead of silently
leaving you connected to nothing. Close it when done:

```bash
pkill -f 'ssh.*15432:127.0.0.1:5432'
```

The DB password lives in `~/vocabulary-app/.env` on prod as `POSTGRES_PASSWORD`. Source it
into a variable in the **same** shell invocation that uses it, and never echo it:

```bash
PW=$(ssh -o BatchMode=yes -i ~/.ssh/id_ed25519_cow_prod michael@174.127.171.187 \
      'grep -m1 "^POSTGRES_PASSWORD=" ~/vocabulary-app/.env | cut -d= -f2-')
```

## What this does and does not authorize

SSH access removes a *logistics* barrier, not a *judgment* one. Everything the deploy rules
already required still applies:

- **Rebuilding prod containers takes the live site down.** Confirm with the user before
  `docker-compose -f docker-compose.prod.yml down` / `up --build`, unless they already said
  to proceed.
- **Never** `docker-compose -f docker-compose.prod.yml down -v` — `-v` destroys the
  `cow-prod_postgres_data` volume holding all real user data.
- Derive pending migrations from `schema_migrations` and `migrate.sh --dry-run`, never from
  a runbook's status banner (see CLAUDE.md — stale banners have caused this repeatedly).
- Read-only inspection first. Prefer one batched read over many small writes.

## Verifying you are where you think you are

Prod and dev are easy to confuse because both run Docker and both hold the repo. Check:

```bash
hostname                                    # beech-2025 = prod
docker ps --format '{{.Names}}' | sort      # cow-*-prod = prod, cow-*-local = dev
head -3 ~/vocabulary-app/amIOnTheProdMachine.md
```
