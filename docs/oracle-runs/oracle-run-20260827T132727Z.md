## Promotion blocker — found and fixed mid-round

First `promote-discoverable.js --words=<batch>` dry-run reported **all 25 "not
ready"**, citing tones/numbered-pinyin/process-definitions-array/classifier as
unmet, despite each having reported "done" and `check-manifest-sync.js` showing
zero drift across all 24 zh/es manifest steps.

**Root cause**: `backfill-tones`, `backfill-numbered-pinyin`, and
`backfill-classifier` each gate row selection on the target *column* being NULL,
not on the `enrichmentLog` stamp. This batch had legacy non-NULL
`tone`/`numberedPinyin`/`classifier` values from before stamping existed, so the
scripts silently processed 0 rows and exited "success" without ever writing the
stamp. Separately, 起 specifically had a genuine unstamped
`process-definitions-array` gap (发起, same batch, was correctly stamped — not a
systemic pattern).

**Fix**: re-ran all four with `--stale --words=<batch>`. Tones/numbered-pinyin/
classifier converged in one clean pass each. `process-definitions-array` does
**not** actually implement a `--stale` flag (confirmed by source read — no `stale`
reference in the script) — the flag was silently ignored and it always re-runs its
unconditional `HAS_WORK_CLAUSE` query. It took 6 export/apply rounds to converge:
白起/起动/起子 needed their short-gloss stage answered (first definitions exceeded
the 20-char headline limit), triggering a fresh Pass-1+critic round on the
newly-reshaped rows; 起 additionally cycled through an extra Pass-1→critic pass
before its reordered definitions array reached a stable fixed point (confirmed
unchanged across two subsequent full-batch re-runs).

**Follow-up worth tracking**: `backfill-process-definitions-array.js` lacking
`--stale` support is an inconsistency against the rest of the manifest (which
uses stamp+version staleness uniformly) — worth a future fix so a version bump to
this script re-triggers only stale rows rather than the whole `HAS_WORK_CLAUSE`
universe every run. Not changed this round (out of scope for an oracle run).
