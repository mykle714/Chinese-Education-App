## 4. Code changes

### 4a. NEW: `server/scripts/backfill/spanish/mark-discoverable.js`

**Layer:** data-enrichment (backfill) orchestration — the Spanish counterpart of `promote-discoverable.js`.

**Why:** CLAUDE.md forbids setting `discoverable = TRUE` via a hand-written `UPDATE`; it must go through pipeline code. Chinese has had `promote-discoverable.js` since 2026-07-21, but Spanish had none, so `/mark-discoverable` §B2 still instructed a bare `UPDATE` — exactly the statement the auto-mode permission classifier blocks. This script closes that hole: same effect, but the row selection, the eligibility bar, and a dry-run review all live in reviewable code.

**Why the bar differs from zh's promoter:** `promote-discoverable.js` flags a row only *after* the whole manifest has enriched it. The es pipeline runs the other way around — §B3's AI steps auto-scope to `discoverable = TRUE`, so the flag is what *selects* a word for enrichment, not what certifies completion (and there is no es manifest to check against). So the es bar is "is this a real headword worth enriching":
1. word exists in `dictionaryentries_es`,
2. its representative row has a non-empty `definitions` array,
3. that row is not a pointer stub (`alternative form of…`, `abbreviation of…`).

**Representative-row pick:** es rows are split by `(pos, gender)` until §B3 collapses them, and that step rebuilds *every* row sharing the `word1`. So flagging one row per word suffices — the script picks the highest-priority content-POS row (verb/noun over adj over adv/interj), then most definitions, then lowest id. This ordering was **added after a real miss**: the naive "most defs, lowest id" pick chose the one-gloss *interjection* rows of `fuego` and `nombre` over their noun rows. (`POS_RANK` fix.)

**Flags:** `--words=` (required), `--apply` (default dry-run), `--undo` (clears `discoverable` on the given words, through the same reviewable path — used to withdraw `negro`, see §6).

### 4b. No changes to any enrichment script.

The five AI backfill scripts and the deterministic cleanup scripts were run exactly as-is.

## 8. Findings to surface (design issues, not run failures)

1. **Spanish has no manifest.** `server/scripts/backfill/shared/lib/requiredScripts.js` and `oracle-plan.js` are zh-only, so `oracle-plan.js` cannot plan es and `promote-discoverable.js` cannot promote es. This is *why* es still needed a dedicated `mark-discoverable.js` (§4a) rather than reusing the zh promoter. **Fix:** build an es manifest + es support in the planner/promoter; then `spanish/mark-discoverable.js` could be folded into a completeness-gated promoter like zh's.

2. **Only 3 of 8 es scripts stamp `enrichmentLog`.** `backfill-icons` (v1), `spanish/backfill-long-definitions` (v2), `spanish/backfill-vernacular-score` (v2) stamp; `split-semicolon-definitions`, `expand-abbreviations`, `parts-of-speech`, `process-definitions-array`, and `example-sentences` write **no** stamp. There is therefore no version-staleness signal for those five, and an es manifest cannot be built until they stamp. **Fix:** add `stampEntries`/`initRunLog` to the five unstamped es scripts.

3. **The deterministic es cleanup scripts ignore `--words`.** `backfill-split-semicolon-definitions.js` and `backfill-expand-abbreviations.js` scan the whole 121k-row corpus regardless of `--words=` (they reported "121029 total entries" / "0 changed" each time). Harmless here (idempotent, 0 changes), but the flag is silently a no-op for them — worth either honoring `--words` or documenting that they are corpus-wide only.

4. **The es long-definition prompt omits the row's `definitions` array.** Unlike zh, the es long-def generator receives only `Word:` + `Parts of speech:`, so the answerer must supply each sense from its own knowledge rather than from the entry's actual glosses. A genuine quality risk — it is the mechanism by which a wrong sense (e.g. a narrow/derogatory reading) could enter a long definition before the validator catches it. **Fix:** pass the row's ranked `definitions` into the long-def user prompt.

5. **Column naming inconsistency:** `dictionaryentries_es` uses `iconId` (FK → `icons8`), whereas some survey queries and habits assume `iconUrl`. Minor, but a recurring stumble.
